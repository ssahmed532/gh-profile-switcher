GitHub Profile Switcher

Use your Spursol and personal GitHub accounts on one Windows laptop. Each repo gets the right name, email, signing key and push account automatically, based on the folder it is in.

Version 1.5Last updated 2026-09-30Tested with Git 2.55, gh 2.101, GCM 2.9, PowerShell 7
Overview

How it works

The folder a repo is in decides which identity git uses. Nothing has to be switched for git. Repos under your personal folder use the personal profile, and every other repo uses the work profile, as they do today.

The folder rule applies only inside a git repo. Git checks the rule against the repo's .git folder, so in a directory that is not a repo, including E:\personal itself, git uses the work profile. A repo you create or clone anywhere under E:\personal\ gets the personal profile.

One-time · about 10 minutes

Setup

Run the commands from a PowerShell window in E:\personal\gh-profile-switcher. Tick each step as you finish it. The page remembers your ticks in this browser.

  1. 1

    Choose the personal folder

    All personal repos will live under one folder. The default is E:/personal/, and setup creates it if it is missing. Any folder works, as long as no work repo will ever sit inside it.

    If you already have personal repos elsewhere, move them into this folder after setup. Moving the folder is all that is needed.

  2. 2

    Fill in profiles.json

    Copy profiles.example.json to profiles.json and replace every REPLACE-ME value. Change root if you chose a different folder in step 1. profiles.json is git-ignored, so your real names and emails stay out of the repo.

    profiles.json
    {
  "default": "work",
  "profiles": {
    "work": {
      "name": "REPLACE-ME",
      "email": "REPLACE-ME@work.example",
      "ghUser": "REPLACE-ME",
      "signingKey": "~/.ssh/id_ed25519.pub"
    },
    "personal": {
      "name": "REPLACE-ME",
      "email": "REPLACE-ME@gmail.com",     // verified email, or the noreply address
      "ghUser": "REPLACE-ME",               // personal GitHub username
      "signingKey": "~/.ssh/id_ed25519_personal.pub",
      "root": "E:/personal/"
    }
  }
}

    The // comments above are for this guide only. JSON does not allow comments, so do not add them to the file.

  3. 3

    Choose the personal signing key

    Each account signs with its own SSH key. Choose one of these:

    • New key (recommended). Leave signingKey as it is. setup runs ssh-keygen for you in step 4.
    • Existing key. Copy both files of the key pair into ~/.ssh: the private key and its .pub file, with the same name except for the .pub ending (for example id_ed25519_personal and id_ed25519_personal.pub). Then set signingKey to the .pub path.
    The private key must sit next to the .pub file

    Git signs by running ssh-keygen with the .pub path. With ssh-agent disabled, as it is on this laptop, ssh-keygen loads the private key from the same path without .pub. If that file is missing, every signed commit fails. setup stops with an error when a .pub file has no private key next to it.

    Why not reuse the work key

    A separate key keeps the two accounts independent. Removing the work key when you leave Spursol, or rotating it, does not affect your personal commit signatures.

  4. 4

    Run setup

    PowerShell
    .\ghprofile.ps1 setup

    If a new key is generated, you are asked for a passphrase. The passphrase protects the key. With ssh-agent disabled on this laptop, git will ask for it each time it signs a commit. Leave the passphrase empty if you don't want that prompt.

    What setup changes:

    • Copies ~/.gitconfig to ~/.gitconfig.bak-<timestamp>
    • Sets the work name, email, signing key and push account in ~/.gitconfig
    • Writes ~/.gitconfig-personal and adds the folder rule that loads it
    • Creates the personal folder and, if missing, the personal signing key
    • Adds each signing key to ~/.ssh/allowed_signers so git can verify signatures locally

    It ends by printing the commands for steps 5 to 7. It is safe to run again. Repeat runs don't create duplicate entries.

    If PowerShell refuses to run the script

    Run Unblock-File .\ghprofile.ps1 once, or run it with pwsh -ExecutionPolicy Bypass -File .\ghprofile.ps1 setup.

  5. 5

    Sign in to gh as the personal account

    This adds a second account to gh. The work login stays. Before you run it, sign in to github.com in your browser as the personal account, or use a private window, so the browser approves the right account.

    PowerShell
    gh auth login --hostname github.com --git-protocol https --web --scopes write:ssh_signing_key

    write:ssh_signing_key allows gh to upload the signing key in the next step. GitHub doesn't grant this permission by default. After sign-in, the personal account becomes the active gh account.

  6. 6

    Upload the personal signing key

    With the personal account active, upload the public key as a signing key:

    PowerShell
    gh ssh-key add $HOME/.ssh/id_ed25519_personal.pub --type signing --title "$env:COMPUTERNAME signing"

    To use the website instead: github.com/settings/keys → New SSH key → set Key type to Signing Key → paste the contents of the .pub file.

    The work key should already be on your-work-user as a signing key, because your work commits are already signed. Check at github.com/settings/keys while signed in as that account.

  7. 7

    Switch gh back to work

    PowerShell
    .\ghprofile.ps1 switch work

    Work is your main account, so keep gh on it by default. switch prints status afterwards.

  8. 8

    Verify both identities

    Make a throwaway repo in the personal folder, make a signed commit, and check the signature:

    PowerShell
    git init E:\personal\signing-test
cd E:\personal\signing-test
E:\personal\gh-profile-switcher\ghprofile.ps1 status
git commit --allow-empty -m "signing test"
git log --show-signature -1
    • status shows personal, your personal email and id_ed25519_personal.pub.
    • git log --show-signature shows Good "git" signature for your personal email.
    • Run status in any work repo. It shows work and you@work.example.

    First push from a personal repo: Git Credential Manager opens a sign-in window once for the personal account and remembers it. To confirm both accounts are stored, run:

    PowerShell
    git credential-manager github list

    After you push, the commit shows Verified on GitHub. Delete E:\personal\signing-test when you're done.

Checking

Reading status

Run status inside a repo. It shows what git and gh will use in that directory. Example from a personal repo while gh is still on work:

Output
Directory      : E:\personal\blog
git profile    : personal
git identity   : Your Name <you@gmail.com>
git signing key: C:/Users/you/.ssh/id_ed25519_personal.pub
git push as    : your-personal-user
gh CLI as      : your-work-user
WARNING: gh CLI is 'your-work-user' but this directory is 'personal'. Run: .\ghprofile.ps1 switch personal
LineMeaning
git profileThe profile whose email matches this repo's effective user.email. <none matched> means the repo overrides the email itself. <none - not inside a git repo> means the folder rule does not apply here (see How it works). The output then skips the git lines and prints the folder rule instead, as shown below.
git identityThe author name and email for new commits
git signing keyThe key used to sign new commits
git push asThe GitHub account Git Credential Manager uses for push and fetch
gh CLI asThe active gh account. The warning appears only inside a repo, and only when this differs from the repo's profile. It affects gh commands only, never commits or pushes.

Outside a repo, status (and switch, which prints it) shows only the gh account and the folder rule. It leaves out the git lines, because there they would show the work defaults even after switch personal:

Output
Directory      : E:\personal\gh-profile-switcher
git profile    : <none - not inside a git repo>
gh CLI as      : your-personal-user

Git picks the identity per repo: repos under E:/personal/ use 'personal'; all other repos use 'work'.
Run status inside a repo to see the identity it will use there.
When something is off

Troubleshooting

A commit has the wrong email

Usual cause: the repo is not under the personal folder, or the repo sets its own user.email.

See where the email comes from:

PowerShell
git config --show-origin user.email

If the value comes from .git/config, remove it with git config --unset user.email. To fix the last commit before it is pushed, run git commit --amend --reset-author --no-edit.

Push fails with "Permission denied" or 403

Usual cause: the push used the other account.

Check the git push as line in status. If the remote URL contains a username (https://someone@github.com/…), that username takes priority. Remove it with git remote set-url origin https://github.com/<owner>/<repo>.

If a stored login is broken, remove that account from Git Credential Manager and push again to sign in fresh:

PowerShell
git credential-manager github list
git credential-manager github logout <account>
GitHub shows the commit as "Unverified"

Usual causes: the key was uploaded as an authentication key instead of a signing key, or the commit email is not verified on that account.

At github.com/settings/keys, the key must be listed under Signing keys. At github.com/settings/emails, the commit email must show as verified. After fixing it, push a new signed commit to confirm it shows Verified.

Push rejected because it would publish a private email

Cause: the personal account blocks command-line pushes that expose its email.

Put the account's noreply address (shown at github.com/settings/emails) in profiles.json, run setup again, and amend the unpushed commits with git commit --amend --reset-author --no-edit.

gh ssh-key add says a scope is missing

Grant the scope to the active account, then retry step 6:

PowerShell
gh auth refresh --hostname github.com --scopes write:ssh_signing_key
switch says gh has no login for the account

That account was never added to gh, or it was signed out. Repeat step 5.

Git asks for a passphrase on every commit

This is expected when the signing key has a passphrase and ssh-agent is disabled, as it is on this laptop. This guide does not cover agent setup.

Commit fails with "No private key found for public key"

Cause: only the .pub file is in ~/.ssh, and its private key is missing. See the warning in step 3.

Copy the private key into ~/.ssh under the same name without .pub, then commit again. If you no longer have the private key, delete the .pub file, run setup to generate a new pair, and repeat step 6 to upload it.

Limits

  • The gh CLI account is global. status warns when it doesn't match the directory, but it doesn't switch it for you.
  • HTTPS remotes only. SSH remotes would need a host alias for each account in ~/.ssh/config.
  • A username embedded in a remote URL overrides the profile's push account.
  • Browser sessions on github.com are not managed.
