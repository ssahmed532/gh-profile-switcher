GitHub Profile Switcher

Folder-based Git identities, explicit GitHub CLI switching, and diagnostics that distinguish configuration from authentication.

1. Setup

Install PowerShell 7.2+, Git 2.34+, a GitHub CLI version supporting multi-account switching and JSON auth status, and an SSH-signing-capable OpenSSH installation. Signing profiles need ssh-keygen; agent mode also needs ssh-add. A credential helper such as Git Credential Manager is needed for convenient HTTPS authentication. Setup does not install software or change credential helpers.

pwsh -NoProfile -File ./ghprofile.ps1 --version
# Prints exactly: v0.3.0
Copy-Item profiles.example.json profiles.json
# Edit every REPLACE-ME value and choose roots for this computer.
./ghprofile.ps1 setup -WhatIf
# If keys do not exist, create them separately:
./ghprofile.ps1 init-key work
./ghprofile.ps1 init-key personal
./ghprofile.ps1 setup
# Run inside each repository:
./ghprofile.ps1 doctor

Only run init-key for a new pair. Setup validates every profile and signing key before activating any configuration. It does not generate keys, create repository roots, log in, upload keys, or push anything.

Setup shares status's rich console styling. Its PLAN section lists the global configuration destination, policy, roots and signing modes. VALIDATION shows per-profile key results; CONFIGURATION reports staging; COMPLETE appears only after activation succeeds, followed by the backup location and a doctor command. A fresh installation explicitly explains why no backup was necessary.

setup -WhatIf displays a PREVIEW without validating keys or writing configuration. setup -Plain uses plain text, and setup -Color Always forces rich output. Failures appear in red on stderr with exit 1. UTF-8 is used for rich console writes and the caller's output encoding is restored immediately afterward.

Use -ConfigPath /absolute/path/profiles.json to keep personal configuration outside this checkout. The default is profiles.json beside the script. It is git-ignored; do not commit private keys, tokens, or your personal configuration.

2. Configuration and identity policy

{
  "schemaVersion": 1,
  "policy": "strict",
  "profiles": {
    "work": {
      "name": "Work Example",
      "email": "work@example.com",
      "ghUser": "your-work-user",
      "host": "github.com",
      "roots": ["C:/work/"],
      "signingMode": "file",
      "signingKey": "~/.ssh/work-signing.pub"
    },
    "personal": {
      "name": "Personal Example",
      "email": "personal@example.com",
      "ghUser": "your-personal-user",
      "roots": ["C:/personal/", "D:/personal/"],
      "signingMode": "file",
      "signingKey": "~/.ssh/personal-signing.pub"
    }
  }
}
FieldBehavior
policy: strictRecommended for separation. Every profile needs roots. The managed base clears inherited user name/email, so ordinary commits outside the roots fail instead of silently using work identity.
policy: default, default: workConvenience fallback: unmatched repositories use work. The default profile can omit roots. Explicit roots on all profiles are honored. Omitting policy preserves the original default behavior.
root or rootsOne absolute path or an array of paths; ~/ is supported. Use one field, not both. Roots cannot overlap or contain glob characters. Missing folders are allowed but are not created.
hostDefaults to github.com. Set an enterprise hostname per profile when needed.
signingModefile (default), agent, or none. None explicitly disables automatic commit signing for that profile.
signingKeyAbsolute or ~/ public-key path ending in .pub. File mode uses the adjacent private key; agent mode uses the public key with a matching key loaded in the agent.
schemaVersion1. Optional for old configurations. Unknown versions, misspelled fields, unsafe identifiers, placeholders, and invalid values fail validation.

Strict mode is a guard against mistakes, not an access-control boundary. Local Git settings, command-line options and environment variables can still override configuration. It does not prevent pushes from an unmatched repository.

3. Daily use and diagnostics

./ghprofile.ps1 switch personal
./ghprofile.ps1 status
./ghprofile.ps1 status -Plain
./ghprofile.ps1 status -Color Never
./ghprofile.ps1 status -Verbose
./ghprofile.ps1 status -Json
./ghprofile.ps1 doctor -Json -NonInteractive
./ghprofile.ps1 --version

switch changes only the shared active GitHub CLI account for the profile's host, then checks that account's authentication state. Every terminal using the same gh configuration sees that change. It never changes repository identity. Applicable environment tokens block switching with an explanation; their values are not printed. A network/auth failure after switching is reported, but the selected account may already have changed.

In an interactive terminal, status uses a cyan title and section headings, green authentication indicators, amber warnings and standard Unicode symbols. Identity, Git remotes, GitHub CLI and attention items are grouped into separate sections. No Nerd Font or additional module is required. Long values and warnings wrap with hanging indentation to fit the terminal (up to 96 columns), and identical author/committer values are shown once.

-Plain restores the compact ASCII-friendly layout. -Color Never keeps the rich layout without ANSI colors; -Color Always explicitly enables rich ANSI output even when redirected. The default -Color Auto uses plain output when redirected or piped, and suppresses colors when NO_COLOR is set, TERM is dumb, or PowerShell's OutputRendering is PlainText. Plain takes precedence over Color. JSON output is unaffected.

The rich view writes directly to terminal standard output so PowerShell cannot silently remove explicitly requested colors. For PowerShell variable assignment or pipeline processing, use -Plain or -Json. No terminal settings or caller preferences are changed.

Use -Verbose for full configuration paths, origins and credential helpers, or -Json for all structured details. A missing managed marker is reported as legacy/unapplied setup, not as proof of a wrong identity; the matching legacy public-key path is covered by the migration warning. Authentication to push destinations remains unverified: reading a username or authenticating gh does not establish the account Git will use.

doctor adds signing-key validation and returns exit 2 when it finds issues. It detects local/environment identity overrides, signing mismatches, CLI account/auth problems, absent HTTPS helpers, SSH remotes, and linked-worktree metadata selection. Run it inside each repository. Outside a repository it can inspect CLI authentication, but cannot verify repository identity.

ExitMeaning
0Command completed; status can still contain diagnostic warnings.
1Usage, validation, dependency, native-command or operational failure.
2Doctor completed and found issues requiring attention.

-Json is supported by status/doctor and emits a single JSON document; fatal errors use an Error field. -WhatIf previews setup, switch and init-key without writing configuration, generating keys or switching accounts. Setup previews validate profile data, but full key validation occurs only when applying.

4. Signing keys

In file mode, setup validates the public key and derives its public counterpart from the private key to ensure they match. The Git signing setting explicitly uses the private-key path. Encrypted keys may prompt for a passphrase. In agent mode, setup checks that the public key is loaded in ssh-agent and does not require an adjacent private-key file.

init-key is interactive, prompts for a passphrase, and refuses to run if either key file already exists. Keep private keys protected by your operating system's permissions and use a passphrase. For automation, provision keys separately or use an agent. -NonInteractive never prompts; encrypted file keys fail validation unless you switch to agent mode. It does not silently generate unencrypted keys.

If only the public key is missing, recover it from the existing private key instead of generating a replacement:

ssh-keygen -y -f ~/.ssh/work-signing
# Save the returned PUBLIC key to work-signing.pub after confirming the path.
# Never overwrite the private key.

Setup enables gpg.format=ssh and commit.gpgsign=true for signing profiles and creates a managed allowed-signers file for local verification. Existing global allowed-signers entries are copied, never edited in place; historical trusted keys are retained across generations. Revocation is a separate explicit action using Git's SSH revocation configuration. An existing missing or relative allowed-signers path must be resolved before setup.

For each account, including the default, log in and register its public key as a signing key:

gh auth login --hostname github.com --git-protocol https --web --scopes write:ssh_signing_key
./ghprofile.ps1 switch personal
# Confirm the active login matches the intended account before uploading.
$env:GH_HOST = 'github.com'
gh ssh-key add "$HOME/.ssh/personal-signing.pub" --type signing --title "This computer signing"

Use your profile's actual host and key path. A verified commit email and correct GitHub signing-key registration are required for GitHub's Verified display; local verification alone does not prove those account settings. Key uploading is intentionally manual.

5. Git and GitHub CLI credentials

Git commit identity, commit signing, Git transport credentials and gh API credentials are independent. For HTTPS, configure a trusted credential helper with both accounts; the profile supplies a username hint for its host. First access may require a helper login. Setup leaves existing helper configuration untouched. Do not assume gh auth login configured the same credential store used by Git.

For SSH remotes, configure account-specific SSH authentication keys/host aliases independently. The signing key is not automatically the SSH transport key. Status will flag this distinction. A successful push or authorized read is an external authentication test; this tool does not initiate one.

GitHub CLI tokens in GH_TOKEN/GITHUB_TOKEN, or their enterprise equivalents, override stored accounts. Remove the override from the invoking environment when switching stored identities. Account changes are global to the shared CLI configuration; concurrent terminal users should coordinate switches or use separate GH_CONFIG_DIR directories.

6. Safe setup, migration and recovery

Setup honors GIT_CONFIG_GLOBAL. Otherwise it writes ~/.gitconfig, or an existing XDG git/config when ~/.gitconfig does not exist. Managed generations live beside that file in <global-config>.ghprofile/<generation>/.

  1. Validate the complete configuration and all signing keys.
  2. Acquire the standard global Git config lock. A competing Git writer or setup run causes a clear failure.
  3. Stage a copy of global configuration and generate new profile files, allowed signers and a manifest.
  4. Detach previous includes bearing this script's ownership marker, including the original script's generated includes; preserve unrelated includes and original files.
  5. Append a newly serialized managed include at the end, validate generated Git syntax, back up the original global file, then atomically replace it.

A failure before activation leaves the active configuration unchanged. Rerunning setup reconciles profile removals, root moves and default changes. Old generations, backups and trust entries are retained for recovery; unchanged reruns are behaviorally idempotent but intentionally produce a new generation. No private keys or tokens are stored in generations.

Legacy global name/email/credential values are preserved but overridden by the managed include. This avoids deleting settings whose ownership cannot be proved. Migration checks includes in the global file being edited; conflicting settings from other configuration sources are surfaced by doctor. Manually edited legacy files without the ownership marker are treated as user-managed files.

To roll back, close concurrent configuration writers and restore the exact global backup printed by setup. Earlier generation paths are retained, so a backup referencing them remains usable. On a fresh installation with no prior global file, remove only the managed include after inspecting the file. Do not blindly restore an old backup over subsequent unrelated edits. Remove unused generation directories only after confirming no current configuration or retained backup references them. Never delete signing keys as part of uninstall.

After a killed process, a stale <global-config>.lock may remain. Confirm no Git/configuration process is using it before manually removing it. A crash can leave an unreferenced generation; it does not activate partial configuration.

7. Supported boundaries

  • Folder rules use Git's gitdir metadata path, case-insensitive on Windows. Linked worktrees and submodules may therefore follow the main repository's metadata location. Status explains this. Use ordinary checkouts for strict folder separation.
  • Use canonical physical roots; symlinks, junctions and case-sensitive Windows directories can differ from the chosen matching policy. Doctor compares expected and effective identity but cannot enforce future commands.
  • Local config, environment variables and later global edits can override generated settings. Run doctor after changing any of them.
  • The atomic transaction covers Git configuration activation. Key creation and CLI account switching are separate operations. Network diagnostics have a 30-second per-command timeout; interactive key prompts have no timeout.
  • No account login, key upload, credential-helper installation, SSH transport configuration, remote push, ACL repair, key revocation or old-generation deletion is performed automatically.
  • Windows is the verified platform for this release; POSIX path matching is implemented but requires platform-specific validation before deployment.

8. Tests and versioning

pwsh -NoProfile -File tests/Run-Tests.ps1
pwsh -NoProfile -File tests/Render-Status.ps1
pwsh -NoProfile -File tests/Render-Status.ps1 -Preview

The dependency-free suite uses temporary repositories, isolated Git/gh configuration, disposable SSH keys and mocked authentication responses. It exercises signing/verification, setup reconciliation, strict mode, migration, worktrees, input serialization, failure isolation, agent mode and version output. It never switches real accounts or uploads keys. Temporary fixture paths are printed for inspection.

The release version has a single source in $ScriptVersion in ghprofile.ps1. --version and -Version print only v0.3.0 before config or dependency checks. The initial release was 0.1.0; 0.1.1 fixed console readability, 0.2.0 added rich status output, and 0.3.0 extends styling to setup under Semantic Versioning 2.0.0.

The versioned interface consists of documented commands, parameters, profile schema, exit codes and JSON fields. In 0.x releases, compatible fixes increment PATCH and feature/breaking interface changes increment MINOR, with changes documented in CHANGELOG.md. Starting at 1.0.0, breaking changes increment MAJOR. Keep release documentation and version tests synchronized; schemaVersion changes independently when the configuration schema becomes incompatible.
